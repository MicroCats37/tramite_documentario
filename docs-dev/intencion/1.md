# Arquitectura Funcional del Flujo de Solicitudes y Áreas

## 1. Objetivo

El propósito de esta arquitectura es permitir que una solicitud pueda ser gestionada por múltiples áreas de forma simultánea y flexible, eliminando la dependencia de un flujo estrictamente lineal.

El modelo debe permitir, entre otros escenarios:

* múltiples áreas trabajando en paralelo;
* una misma área entrando y saliendo del trámite varias veces;
* derivaciones entre áreas;
* devoluciones y rebotes entre áreas;
* áreas que abandonan una intervención sin necesariamente derivarla;
* uno o varios usuarios trabajando por cada área;
* conservación completa del histórico;
* conocimiento rápido del estado actual;
* evitar duplicar innecesariamente la relación `Solicitud ↔ Área`.

Los campos indicados son **referenciales**. La intención de este documento es definir responsabilidades y comportamiento de las entidades, no cerrar todavía el diseño físico definitivo.

---

# 2. Modelo conceptual general

El núcleo queda compuesto por:

```text
EXPEDIENTE
    │
    │ 1:1
    ▼
SOLICITUD
    │
    ├── SOLICITUD_ESTADO_HISTORIAL
    │
    └── SOLICITUD_ASIGNACION
            │
            ├── SOLICITUD_ASIGNACION_PERIODO
            │
            ├── SOLICITUD_ASIGNACION_USUARIO
            │
            └── SOLICITUD_DERIVACION
```

Cada nivel responde a una responsabilidad diferente:

| Entidad                      | Responsabilidad                                         |
| ---------------------------- | ------------------------------------------------------- |
| `Expediente`                 | Información objetiva y documental ingresada             |
| `Solicitud`                  | Trámite o caso global                                   |
| `SolicitudEstadoHistorial`   | Evolución del estado global                             |
| `SolicitudAsignacion`        | Participación de un área en la solicitud                |
| `SolicitudAsignacionPeriodo` | Cada ciclo temporal de participación activa de esa área |
| `SolicitudAsignacionUsuario` | Personas que trabajan por el área                       |
| `SolicitudDerivacion`        | Movimiento formal entre áreas/períodos                  |

---

# 3. Expediente

`Expediente` representa fundamentalmente los datos objetivos recibidos.

Ejemplo referencial:

```text
Expediente
----------
id
numero_expediente

datos_interesado
tipo_documento
numero_documento

asunto
folios

archivo_principal
fecha_ingreso

creado_por
...
```

El expediente no debería encargarse del flujo interno.

Conceptualmente:

> Expediente responde a: **¿Qué ingresó al sistema?**

---

# 4. Solicitud

`Solicitud` representa el trámite asociado al expediente.

Relación conceptual:

```text
Expediente 1 ───── 1 Solicitud
```

Ejemplo:

```text
Solicitud
---------
id
expediente_id

estado_global

fecha_inicio
fecha_cierre

tipo_tramite
prioridad
...
```

La solicitud representa:

> **El caso administrativo completo que está siendo procesado.**

No representa específicamente a qué área pertenece actualmente.

---

# 5. Estado global de Solicitud

La solicitud puede conservar un estado actual como:

```text
CREADA
EN_PROCESO
OBSERVADA
LISTA_PARA_CIERRE
FINALIZADA
ANULADA
```

Los valores definitivos dependerán posteriormente del negocio.

Este estado debe representar la situación global del trámite.

Ejemplo:

```text
Solicitud #100
estado_global = EN_PROCESO
```

aunque internamente pueda existir:

```text
Arquitectura → FINALIZADA
Estructuras  → EN_PROCESO
Eléctrica    → PENDIENTE
```

---

# 6. SolicitudEstadoHistorial

Además del estado actual, cada transición importante debe quedar registrada.

```text
SolicitudEstadoHistorial
------------------------
id
solicitud_id

estado_anterior
estado_nuevo

fecha
cambiado_por

motivo
observacion
...
```

Ejemplo:

```text
08:00  CREADA → EN_PROCESO
15:30  EN_PROCESO → OBSERVADA
10:15  OBSERVADA → EN_PROCESO
18:00  EN_PROCESO → FINALIZADA
```

Esta tabla representa historial funcional.

Puede mantenerse adicionalmente Django Simple History como mecanismo de auditoría técnica.

---

# 7. SolicitudAsignacion

`SolicitudAsignacion` representa:

> **La participación institucional de un área determinada dentro de una solicitud.**

Esta entidad se mantiene estable aunque el área entre y salga varias veces del flujo.

Ejemplo:

```text
Solicitud #100
│
├── SolicitudAsignacion #1
│   Área Arquitectura
│
├── SolicitudAsignacion #2
│   Área Estructuras
│
└── SolicitudAsignacion #3
    Área Eléctrica
```

En este modelo debería existir conceptualmente una única relación:

```text
Solicitud + Área
```

por lo que puede plantearse:

```text
UNIQUE(solicitud_id, area_id)
```

---

# 8. ¿Por qué no crear otra SolicitudAsignacion cada vez que vuelve el área?

Porque ahora diferenciamos:

```text
ASIGNACIÓN
```

de:

```text
PERÍODO DE ASIGNACIÓN
```

La asignación responde:

> ¿Esta área participa o ha participado en esta solicitud?

El período responde:

> ¿Cuándo estuvo activa esa participación y qué ocurrió durante ese ciclo?

Por ejemplo:

```text
SolicitudAsignacion
Área Arquitectura
│
├── Período #1
├── Período #2
└── Período #3
```

Solo existe una asignación de Arquitectura, aunque haya intervenido tres veces.

---

# 9. SolicitudAsignacionPeriodo

Esta entidad registra **cada ciclo o período continuo durante el cual una asignación de área estuvo activa**.

Ejemplo:

```text
SolicitudAsignacionPeriodo
--------------------------
id
solicitud_asignacion_id

estado
tipo_cierre

fecha_inicio
fecha_fin

iniciado_por
finalizado_por

motivo
observacion

secuencia
...
```

Ejemplo real:

```text
Área Arquitectura

Período #1
09:00 → 10:30
DERIVADA

Período #2
12:10 → 13:20
RETIRADA

Período #3
15:00 → actual
ACTIVA
```

---

# 10. El período no es solamente un historial informativo

Aunque contiene información histórica, `SolicitudAsignacionPeriodo` también puede representar el estado operacional actual.

Por ejemplo:

```text
Área Arquitectura
│
├── Período #1 CERRADO
├── Período #2 CERRADO
└── Período #3 ACTIVO
```

El período #3 permite determinar:

> Arquitectura está participando actualmente.

Por tanto, puede utilizarse para decidir:

* si el área puede responder;
* si puede adjuntar documentación;
* si puede derivar;
* si puede finalizar;
* si debe aparecer en la bandeja de trabajo;
* si sus usuarios pueden actuar sobre la solicitud.

---

# 11. Una sola fuente de verdad

Debe evitarse tener simultáneamente:

```text
SolicitudAsignacion.estado = ACTIVA
```

y:

```text
SolicitudAsignacionPeriodo.estado = CERRADO
```

sin una regla clara sobre cuál manda.

La recomendación conceptual es:

> El período actual representa la situación operacional de la asignación.

Por ejemplo:

```text
Existe período abierto
→ asignación actualmente activa

No existe período abierto
→ asignación actualmente inactiva
```

Puede existir un campo redundante como:

```text
SolicitudAsignacion.estado_actual
```

por rendimiento o facilidad de consulta, pero debe actualizarse automáticamente dentro de las mismas transacciones.

Nunca debería modificarse independientemente.

---

# 12. Regla del período activo

Una asignación puede tener N períodos históricos:

```text
Período #1 CERRADO
Período #2 CERRADO
Período #3 CERRADO
Período #4 ACTIVO
```

pero como máximo:

> **un período activo simultáneamente.**

No debería permitirse:

```text
Período #4 ACTIVO
Período #5 ACTIVO
```

para la misma `SolicitudAsignacion`.

Esta regla debería protegerse también a nivel de base de datos cuando sea posible.

---

# 13. Ejemplo de entrada, salida y retorno de un área

Supongamos:

```text
Solicitud #100
```

Arquitectura entra:

```text
SolicitudAsignacion
Área Arquitectura

Período #1
ACTIVO
```

Posteriormente Arquitectura sale:

```text
Período #1
CERRADO
tipo_cierre = RETIRADA
```

No se elimina:

```text
SolicitudAsignacion Arquitectura
```

Posteriormente Arquitectura vuelve a participar.

Se crea:

```text
Período #2
ACTIVO
```

Resultado:

```text
Área Arquitectura
│
├── Período #1
│   RETIRADA
│
└── Período #2
    ACTIVO
```

---

# 14. Derivaciones

Una derivación representa un movimiento formal:

```text
Área A
  ↓
Área B
```

En el nuevo modelo es conveniente relacionarla con los períodos.

```text
SolicitudDerivacion
-------------------
id

periodo_origen_id
periodo_destino_id

derivado_por_id

tipo
motivo
fecha
...
```

---

# 15. Ejemplo de derivación

Arquitectura está activa:

```text
Arquitectura
Período #1
ACTIVO
```

Juan deriva a Estructuras.

En una operación:

```text
1. Cerrar Arquitectura / Período #1

2. Crear o encontrar:
   SolicitudAsignacion Estructuras

3. Crear Estructuras / Período #1

4. Crear SolicitudDerivacion
```

Resultado:

```text
Arquitectura
Período #1
DERIVADA

       │
       │ Juan
       ▼

Estructuras
Período #1
ACTIVO
```

---

# 16. Devoluciones y ping-pong entre áreas

Supongamos:

```text
A → B → A → B → A
```

No se crean cinco `SolicitudAsignacion`.

Se mantienen únicamente:

```text
SolicitudAsignacion Área A
SolicitudAsignacion Área B
```

Sus períodos serían:

```text
Área A
│
├── Período #1
├── Período #2
└── Período #3

Área B
│
├── Período #1
└── Período #2
```

Las derivaciones permiten reconstruir:

```text
A/P1
 ↓
B/P1
 ↓
A/P2
 ↓
B/P2
 ↓
A/P3
```

Esto evita duplicar constantemente las relaciones Solicitud–Área.

---

# 17. Salida sin derivación

No toda finalización de un período implica que exista otra área destino.

Ejemplo:

> Arquitectura determina que ya no necesita participar.

Entonces:

```text
Arquitectura / Período #2

estado = CERRADO
tipo_cierre = RETIRADA
fecha_fin = ...
cerrado_por = Usuario X
motivo = ...
```

No existe `SolicitudDerivacion`.

Conceptualmente:

```text
Área A
  ↓
FUERA DEL FLUJO
```

Posteriormente puede volver mediante un nuevo período.

---

# 18. Tipos de cierre del período

Puede ser útil distinguir por qué terminó un período.

Ejemplos conceptuales:

```text
FINALIZADO
DERIVADO
RETIRADO
RECHAZADO
ANULADO
```

No es necesario conservar exactamente estos nombres.

La intención es distinguir:

### FINALIZADO

El área terminó correctamente su trabajo.

### DERIVADO

El período terminó porque se creó una intervención en otra área.

### RETIRADO

El área dejó de participar sin enviar necesariamente la solicitud a otra área.

### RECHAZADO

El área determinó formalmente que no correspondía atender.

### ANULADO

El período fue invalidado administrativamente.

---

# 19. Asignación de usuarios

Los usuarios siguen estando separados de la participación institucional del área.

```text
SolicitudAsignacion
Área Arquitectura
│
├── Juan
├── Pedro
└── María
```

Puede utilizarse:

```text
SolicitudAsignacionUsuario
--------------------------
id
solicitud_asignacion_id
usuario_id

rol
estado

fecha_inicio
fecha_fin
...
```

Dependiendo de las necesidades posteriores, esta participación también podría relacionarse con un período concreto.

---

# 20. Área vs. usuario

La responsabilidad institucional pertenece al área.

El usuario actúa en representación de ella.

Por ejemplo:

```text
Área Arquitectura
Período actual ACTIVO
```

puede existir aunque:

```text
Usuarios activos = 0
```

Posteriormente Juan toma el trabajo:

```text
Usuarios activos = Juan
```

Después:

```text
Juan sale
Pedro entra
```

pero:

```text
Área Arquitectura
Período actual
```

no necesariamente cambia.

---

# 21. Trabajo paralelo

La arquitectura permite:

```text
                    SOLICITUD
                        │
         ┌──────────────┼──────────────┐
         ▼              ▼              ▼
   Arquitectura    Estructuras      Eléctrica
      P1 activo       P1 activo       P1 activo
```

Las tres áreas pueden trabajar simultáneamente.

Arquitectura no necesita finalizar para que Estructuras comience.

Esto constituye el objetivo principal del rediseño frente al flujo lineal anterior.

---

# 22. Finalización de área y finalización global

Debe distinguirse:

```text
Finalizar período
```

de:

```text
Finalizar Solicitud
```

Un área puede hacer:

```text
Arquitectura / P1
→ FINALIZADO
```

sin que ello implique:

```text
Solicitud
→ FINALIZADA
```

La solicitud deberá aplicar posteriormente reglas globales.

Por ejemplo:

```text
Todas las asignaciones requeridas
tienen su participación satisfecha
        ↓
LISTA_PARA_CIERRE
```

y después:

```text
FINALIZADA
```

---

# 23. Asignaciones requeridas

`SolicitudAsignacion` puede contener información estructural sobre su participación.

Por ejemplo:

```text
tipo_participacion
es_requerida
```

Ejemplo:

```text
Arquitectura   REQUERIDA
Estructuras    REQUERIDA
Eléctrica      REQUERIDA
Legal          CONSULTA
```

Estos campos pertenecen mejor a `SolicitudAsignacion` que a sus períodos porque describen **la relación del área con la solicitud**, no una entrada temporal determinada.

---

# 24. Qué información corresponde a cada entidad

Esta separación es particularmente importante.

## SolicitudAsignacion

Información estable:

```text
solicitud
área
tipo_participacion
es_requerida
configuración
...
```

Responde:

> ¿Qué papel tiene esta área en esta solicitud?

## SolicitudAsignacionPeriodo

Información temporal:

```text
inicio
fin
estado
tipo_cierre
quién inició
quién cerró
motivo
...
```

Responde:

> ¿Qué ocurrió durante esta participación concreta?

---

# 25. Derivaciones como eventos de negocio

`SolicitudDerivacion` no debe depender exclusivamente de Django Simple History.

Representa información administrativa real:

```text
origen
destino
actor
motivo
fecha
```

Ejemplo:

```text
Arquitectura/P1
      ↓
derivado por Juan
      ↓
Estructuras/P1
```

Este evento debe consultarse directamente sin reconstruir cambios históricos de columnas.

---

# 26. Comentarios y adjuntos

Los comentarios y documentos pueden vincularse dependiendo de su alcance.

## Globales

```text
Solicitud
 ├── comentarios
 └── documentos
```

## Propios de un área

```text
SolicitudAsignacion
 ├── comentarios
 └── documentos
```

## Específicos de un ciclo

Si posteriormente es necesario:

```text
SolicitudAsignacionPeriodo
 ├── comentarios
 └── documentos
```

No es obligatorio implementar los tres niveles inicialmente.

La arquitectura simplemente debe permitir diferenciarlos si negocio lo requiere.

# 28. Ejemplo completo

Supongamos una solicitud que requiere:

```text
Arquitectura
Estructuras
Eléctrica
```

Se crean una sola vez:

```text
Asignación Arquitectura
Asignación Estructuras
Asignación Eléctrica
```

Cada una inicia:

```text
Arquitectura P1 ACTIVO
Estructuras  P1 ACTIVO
Eléctrica    P1 ACTIVO
```

Arquitectura finaliza:

```text
Arquitectura P1
FINALIZADO
```

Eléctrica continúa trabajando.

Estructuras deriva a Geotecnia:

```text
Estructuras P1
DERIVADO
```

Se crea:

```text
Asignación Geotecnia
Geotecnia P1 ACTIVO
```

Derivación:

```text
Estructuras/P1
     ↓ María
Geotecnia/P1
```

Geotecnia determina que fue incorrecto y devuelve:

```text
Geotecnia/P1
     ↓ Carlos
Estructuras/P2
```

Ahora la base contiene:

```text
Estructuras
│
├── P1 DERIVADO
└── P2 ACTIVO
```

No existen dos `SolicitudAsignacion` para Estructuras.

# 29. Reglas principales

## Regla 1

Existe como máximo una `SolicitudAsignacion` por:

```text
Solicitud + Área
```

## Regla 2

Una `SolicitudAsignacion` puede tener N períodos.

## Regla 3

Solo puede existir un período activo simultáneamente por asignación.

## Regla 4

Los períodos cerrados nunca se modifican para volver a activarlos.

Si el área vuelve, se crea otro período.

## Regla 5

Una derivación cierra un período origen y abre un período destino.

## Regla 6

Una salida sin destino cierra simplemente el período actual.

## Regla 7

Cambios internos de usuarios no implican necesariamente un nuevo período.

## Regla 8

Varias áreas pueden tener períodos activos simultáneamente.

## Regla 9

Finalizar un período no significa finalizar la solicitud.

## Regla 10

El estado global de la solicitud debe depender de reglas del trámite y no de una única área.

---

# 30. Operaciones transaccionales

Las operaciones estructurales deben ser atómicas.

## Ejemplo: derivar

```text
BEGIN

1. bloquear/verificar período origen

2. cerrar período origen

3. obtener/crear SolicitudAsignacion destino

4. crear período destino

5. crear SolicitudDerivacion

6. actualizar estado global si corresponde

7. guardar históricos correspondientes

COMMIT
```

Esto evita estados parciales o inconsistentes.

# 31. Modelo de autoridad de los datos

Una recomendación importante es definir claramente qué entidad es fuente de verdad.

### Solicitud

Fuente de verdad del:

```text
estado global del trámite
```

### SolicitudAsignacion

Fuente de verdad de:

```text
participación estructural del área
```

### SolicitudAsignacionPeriodo

Fuente de verdad de:

```text
situación operacional actual
y períodos históricos del área
```

### SolicitudDerivacion

Fuente de verdad de:

```text
movimientos formales entre áreas
```

### SolicitudAsignacionUsuario

Fuente de verdad de:

```text
personas que participan por el área
```

# 32. ¿Hace falta otra tabla central?

Con los requerimientos identificados actualmente, no se considera necesaria otra entidad estructural indispensable.

El núcleo queda suficientemente cubierto mediante:

```text
Expediente
Solicitud
SolicitudEstadoHistorial
SolicitudAsignacion
SolicitudAsignacionPeriodo
SolicitudAsignacionUsuario
SolicitudDerivacion
```

Las tablas existentes de:

```text
Área
Usuario
Comentarios
Adjuntos
Auditoría
```

complementan el modelo.

Posteriormente podrían incorporarse entidades específicas como:

```text
SolicitudAsignacionRespuesta
```

si las respuestas formales necesitan versionado, firmas, aprobaciones o estados propios.

Sin embargo, no forman parte obligatoria del núcleo actual.

# 33. Principio final del diseño

La arquitectura se basa en distinguir claramente tres conceptos que anteriormente podían confundirse:

```text
ASIGNACIÓN
= qué área participa

PERÍODO
= cuándo está participando

DERIVACIÓN
= cómo pasó de una participación
  activa hacia otra área
```

Por ejemplo:

```text
Solicitud #100
│
├── Arquitectura
│     ├── P1
│     ├── P2
│     └── P3 ACTIVO
│
├── Estructuras
│     ├── P1
│     └── P2
│
└── Eléctrica
      └── P1 ACTIVO
```

La solicitud conserva un conjunto estable de áreas participantes, mientras que los períodos reflejan la evolución temporal real del proceso.

Esto permite:

* paralelismo;
* reingresos;
* derivaciones;
* devoluciones;
* períodos de inactividad;
* reasignaciones;
* trazabilidad;
* auditoría;

sin duplicar innecesariamente relaciones entre solicitudes y áreas.

## Conclusión

`SolicitudAsignacion` permanece como la entidad principal para representar la relación funcional entre una solicitud y un área.

`SolicitudAsignacionPeriodo` introduce la dimensión temporal y operacional necesaria para conocer cada entrada, salida y reingreso.

La derivación conecta períodos cuando existe un movimiento formal entre áreas.

Con esta separación se obtiene un modelo flexible, trazable y suficientemente abierto para incorporar posteriormente reglas más específicas sin modificar la estructura fundamental del flujo.
