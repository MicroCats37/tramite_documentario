# Diseño Operativo de Notificaciones, Respuestas y Métricas del Flujo

## 1. Objetivo

Este documento complementa la arquitectura principal del flujo de solicitudes y asignaciones.

La intención de esta capa es permitir que el sistema no solamente conozca:

* qué solicitud existe;
* qué áreas participan;
* qué períodos de participación están activos;
* qué usuarios trabajan por cada área;
* qué derivaciones ocurrieron;

sino también que pueda conocer:

* cuándo un área recibió trabajo;
* qué usuarios podían atenderlo;
* quién vio una notificación;
* cuándo la vio;
* quién decidió tomar una asignación;
* cuánto tiempo permaneció sin responsable;
* cuánto demoró un área en reaccionar;
* cuánto demoró en producir una respuesta;
* quién participó en dicha respuesta;
* quién emitió formalmente la respuesta;
* cuánto tiempo tomó resolver la intervención;
* cuántas derivaciones, devoluciones o reingresos ocurrieron;
* cuál es el backlog de cada área;
* cómo se comportan operativamente las áreas y sus usuarios.

Los campos descritos son referenciales y pueden cambiar durante la implementación.

El objetivo principal es definir **la responsabilidad conceptual de cada tabla y las métricas que posteriormente podrán obtenerse**.

---

# 2. Separación fundamental

El sistema debe distinguir claramente tres niveles:

```text
NOTIFICACIÓN
¿El usuario se enteró?

ASIGNACIÓN / AUTOASIGNACIÓN
¿Alguien se hizo cargo?

RESPUESTA / FINALIZACIÓN
¿El área realizó y terminó su trabajo?
```

No deben mezclarse.

Por ejemplo:

```text
Usuario abre una notificación
          ↓
NO significa que tomó el trabajo

Usuario toma el trabajo
          ↓
NO significa que respondió

Usuario responde
          ↓
NO necesariamente significa que
la solicitud completa finalizó
```

Esta separación permitirá métricas mucho más fiables.

---

# 3. Principio institucional

Las solicitudes y asignaciones se dirigen principalmente a un **Área**.

El usuario es un operador que trabaja en representación de esa área.

Por ejemplo:

```text
Solicitud #100
      ↓
Área Arquitectura
      ↓
Juan toma el trabajo
```

A nivel institucional:

> Arquitectura es responsable.

A nivel operativo:

> Juan fue uno de los usuarios que trabajó la asignación.

Esto también aplica a las respuestas.

No debería interpretarse:

> "Juan respondió oficialmente."

Sino:

> "El Área Arquitectura respondió, y Juan fue el usuario que ejecutó o emitió la respuesta."

---

# 4. Flujo operativo completo

Un ejemplo completo puede ser:

```text
Se crea asignación para Área Arquitectura
                ↓
Se abre un período activo
                ↓
Se genera notificación al área
                ↓
Usuarios del área reciben disponibilidad
                ↓
Juan entra al sistema
                ↓
Ve contador de notificaciones
                ↓
Abre listado de notificaciones
                ↓
Abre una notificación concreta
                ↓
Se registra que Juan la vio
                ↓
Juan pulsa "Tomar"
                ↓
Se crea SolicitudAsignacionUsuario
                ↓
Juan empieza a trabajar
                ↓
Juan/Pedro/María participan
                ↓
Área genera una respuesta
                ↓
Respuesta emitida por uno de los usuarios
                ↓
Período finalizado
                ↓
Solicitud continúa o queda lista para cierre
```

Cada paso puede producir métricas diferentes.

---

# 5. Tabla `Notificacion`

## 5.1 Intención

`Notificacion` representa un evento comunicado a un área.

Ejemplos:

```text
Nueva asignación recibida
Solicitud devuelta
Nueva derivación
Nuevo comentario
Área agregada al trámite
Nueva observación
Solicitud próxima a vencer
Solicitud vencida
```

La notificación debe considerarse conceptualmente **inmutable**.

El hecho:

> "Arquitectura recibió una nueva asignación"

no cambia porque alguien la haya visto.

---

# 6. Modelo conceptual de `Notificacion`

Ejemplo referencial:

```text
Notificacion
------------
id                         # BaseModel

area_id

tipo

solicitud_id               nullable
asignacion_id              nullable
periodo_id                 nullable

titulo
mensaje

generada_por_id            nullable
```

Como el `BaseModel` ya contiene:

```text
id
created_at
updated_at
```

no es necesario repetir la fecha de generación.

`created_at` representa:

> cuándo ocurrió/se creó el evento de notificación.

---

# 7. La notificación pertenece al área

Ejemplo:

```text
Notificación #500

Área = Arquitectura
Tipo = NUEVA_ASIGNACION
Asignación = #25
```

Esto significa:

> Arquitectura recibió una nueva asignación.

No significa:

```text
Notificación de Juan
```

ni:

```text
Notificación de Pedro
```

Los usuarios solamente son posibles consumidores de dicho evento.

---

# 8. Tabla `NotificacionUsuario`

## 8.1 Intención

Esta tabla registra la relación individual entre una notificación del área y los usuarios que podían interactuar con ella.

Ejemplo:

```text
Notificación #500
Área Arquitectura
│
├── Juan
├── Pedro
└── María
```

Así es posible conocer el comportamiento de cada operador sin modificar la notificación institucional.

---

# 9. Modelo conceptual de `NotificacionUsuario`

```text
NotificacionUsuario
-------------------
id                         # BaseModel

notificacion_id
usuario_id

vista_at                   nullable
abierta_at                 nullable

descartada_at              nullable   # opcional futuro
```

Restricción:

```text
UNIQUE(notificacion_id, usuario_id)
```

---

# 10. Materialización de destinatarios

Cuando se genera una notificación para un área, puede ser conveniente registrar qué usuarios estaban habilitados para recibirla en ese momento.

Ejemplo:

```text
23/08

Área Arquitectura:
Juan
Pedro
María
```

Se crea:

```text
Notificación #500
│
├── NotificacionUsuario → Juan
├── NotificacionUsuario → Pedro
└── NotificacionUsuario → María
```

Esto es importante para métricas históricas.

Supongamos que un mes después:

```text
Juan deja Arquitectura.
Carlos entra a Arquitectura.
```

No debería concluirse que Carlos tenía responsabilidad sobre una notificación generada antes de pertenecer al área.

Al materializar los destinatarios históricos se conserva:

> quién tenía oportunidad real de atender el evento cuando ocurrió.

---

# 11. Qué significa "vista"

Se recomienda no marcar una notificación como vista simplemente porque el usuario inició sesión.

Tampoco necesariamente porque abrió el panel general.

Ejemplo:

```text
Juan inicia sesión
      ↓
Dashboard muestra:
"5 notificaciones"
```

No ocurre ningún cambio.

Juan abre:

```text
🔔 Notificaciones
```

y ve una lista:

```text
EXP-100
EXP-101
EXP-102
EXP-103
EXP-104
```

Tampoco es necesario cambiar nada todavía.

Cuando Juan abre específicamente:

```text
EXP-102
```

se registra:

```text
vista_at = now()
```

Esta semántica es mucho más precisa.

---

# 12. Vista vs. apertura

Dependiendo de la interfaz, pueden existir dos pasos:

```text
vista_at
```

y:

```text
abierta_at
```

Por ejemplo:

```text
vista_at
= la notificación fue desplegada individualmente

abierta_at
= el usuario navegó al detalle de la solicitud/asignación
```

Sin embargo:

> Si en la aplicación ambos eventos ocurren al mismo tiempo, no es necesario almacenar dos campos.

En ese caso podría mantenerse solamente:

```text
vista_at
```

No conviene almacenar métricas que la interfaz realmente no puede distinguir.

---

# 13. No modificar estado mediante GET

Las operaciones de lectura deberían mantenerse separadas de las acciones que modifican información.

Ejemplo:

```http
GET /notificaciones/
```

solo obtiene información.

No debería marcar automáticamente todo como visto.

Cuando se registra una vista se puede utilizar una operación explícita:

```http
POST /notificaciones/{id}/vista/
```

o una variante en lote:

```http
POST /notificaciones/marcar-vistas/
```

Esto evita que:

* refetches automáticos;
* React Query;
* polling;
* precarga;
* pestañas abiertas;
* peticiones repetidas;

alteren métricas accidentalmente.

---

# 14. Autoasignación

Después de ver la notificación, un usuario puede decidir hacerse cargo.

Ejemplo:

```text
Juan abre EXP-102
      ↓
Lee el detalle
      ↓
Pulsa:
[TOMAR]
```

Entonces se crea:

```text
SolicitudAsignacionUsuario
--------------------------
periodo = Arquitectura/P1
usuario = Juan
...
```

Ese momento tiene un significado completamente diferente de una vista.

---

# 15. Vista vs. autoasignación

```text
VISTA
= Juan conoció el contenido.

AUTOASIGNACIÓN
= Juan aceptó participar operativamente.
```

Una notificación puede ser:

```text
vista = sí
```

pero la asignación:

```text
usuarios activos = 0
```

Por tanto, el trabajo sigue pendiente.

Esta separación es fundamental para las métricas.

---

# 16. Dashboard vs. notificaciones

El dashboard operativo no debería depender exclusivamente del estado de las notificaciones.

Se recomienda separar:

## Campana de notificaciones

```text
🔔 5 eventos nuevos
```

Representa comunicación.

## Dashboard operativo

```text
Área Arquitectura

Pendientes de tomar      5
En proceso               8
Por responder            3
Próximas a vencer         2
Vencidas                  1
```

Representa trabajo real.

Los pendientes deben salir principalmente de:

```text
SolicitudAsignacion
SolicitudAsignacionPeriodo
SolicitudAsignacionUsuario
```

y no de si una notificación fue marcada como vista.

---

# 17. Tabla `SolicitudAsignacionRespuesta`

## 17.1 Cuándo tiene sentido

Esta tabla es recomendable si una intervención de área produce una respuesta formal.

Ejemplos:

* informe;
* pronunciamiento;
* conformidad;
* observación;
* respuesta técnica;
* documento firmado;
* aprobación;
* rechazo formal.

---

# 18. Responsabilidad institucional de la respuesta

Una respuesta pertenece funcionalmente al área.

Ejemplo:

```text
Área Arquitectura
      ↓
Respuesta
```

El sistema debe conservar adicionalmente:

```text
emitido_por = Juan
```

para conocer quién ejecutó la acción.

La lectura correcta sería:

> Arquitectura emitió una respuesta, registrada por Juan.

---

# 19. Modelo conceptual de `SolicitudAsignacionRespuesta`

```text
SolicitudAsignacionRespuesta
----------------------------
id                         # BaseModel

periodo_id

emitido_por_id

tipo_respuesta

contenido                  nullable
archivo                    nullable

estado
fecha_emision              nullable

observacion                nullable
```

---

# 20. Por qué relacionarla con el período

La respuesta debería apuntar preferentemente a:

```text
SolicitudAsignacionPeriodo
```

y no solamente a:

```text
SolicitudAsignacionUsuario
```

Porque:

```text
Arquitectura/P1
│
├── Juan
├── Pedro
├── María
│
└── Respuesta oficial
```

Los tres pudieron participar.

María pudo ser quien finalmente la emitió.

Pero la respuesta pertenece:

```text
Arquitectura/P1
```

no exclusivamente a María.

---

# 21. Estados posibles de una respuesta

Solo si el negocio lo necesita, podría existir:

```text
BORRADOR
EN_REVISION
EMITIDA
ANULADA
RECTIFICADA
```

No es necesario implementar todos inicialmente.

Si solamente existe una respuesta única que se guarda directamente:

```text
contenido
archivo
emitido_por
fecha
```

puede mantenerse más simple.

---

# 22. Múltiples respuestas

Si una misma intervención puede producir:

```text
respuesta inicial
rectificación
respuesta final
```

se justifica:

```text
SolicitudAsignacionPeriodo
        │
        └── 1:N Respuestas
```

Ejemplo:

```text
Arquitectura/P2

Respuesta #1
OBSERVADA

Respuesta #2
RECTIFICACIÓN

Respuesta #3
FINAL
```

Esto permite conservar historial real sin modificar respuestas anteriores.

---

# 23. Respuesta de área vs. respuesta global

Debe distinguirse:

```text
SolicitudAsignacionRespuesta
```

de una eventual:

```text
SolicitudRespuestaFinal
```

La primera representa:

> Resultado de una intervención de área.

La segunda solamente sería necesaria si negocio tiene un documento global final independiente.

Ejemplo:

```text
               Solicitud
                  │
      ┌───────────┼───────────┐
      ▼           ▼           ▼
 Arquitectura  Estructuras  Eléctrica
      │           │           │
 Respuesta A  Respuesta B  Respuesta C
      │           │           │
      └───────────┼───────────┘
                  ▼
        Respuesta Final Solicitud
```

Si no existe ese documento consolidado, no es necesaria otra tabla.

---

# 24. Métricas operativas

Las tablas anteriores permiten medir el comportamiento del proceso sin crear inicialmente tablas específicas de estadísticas.

Las métricas se calculan a partir de eventos y timestamps reales.

---

# 25. Métrica: tiempo hasta primera vista

Permite saber cuánto demoró un usuario en conocer una notificación.

```text
time_to_view =
NotificacionUsuario.vista_at
-
Notificacion.created_at
```

Ejemplo:

```text
Notificación creada: 09:00
Juan la abre:         09:12

Tiempo hasta vista:
12 minutos
```

---

# 26. Métrica: primera reacción del área

Una notificación puede tener varios usuarios.

```text
Juan   vista 09:12
Pedro  vista 09:05
María  vista 09:30
```

La primera reacción del área sería:

```text
MIN(vista_at)
= 09:05
```

Entonces:

```text
Tiempo reacción área
= 5 minutos
```

Esta métrica probablemente sea más importante institucionalmente que cada lectura individual.

---

# 27. Métrica: notificaciones nunca vistas

```text
vista_at IS NULL
```

Permite identificar:

```text
Notificaciones disponibles
pero nunca abiertas por determinado usuario.
```

Debe interpretarse con contexto.

Que un usuario no vea una notificación no necesariamente implica incumplimiento si:

* otro operador ya tomó la asignación;
* no estaba de turno;
* estaba ausente;
* la notificación no requería acción individual de todos.

---

# 28. Métrica: tiempo hasta autoasignación

Una de las métricas más importantes.

```text
time_to_first_claim =
primera asignación de usuario
-
inicio del período
```

Ejemplo:

```text
Área recibe:          09:00
Juan toma:            09:22

Tiempo hasta toma:
22 minutos
```

Responde:

> ¿Cuánto demora un área desde que recibe trabajo hasta que alguien realmente se hace cargo?

---

# 29. Métrica: vista → toma

```text
time_view_to_claim =
fecha autoasignación
-
vista_at
```

Ejemplo:

```text
Juan ve:        09:10
Juan toma:      09:22

12 minutos
```

Esto diferencia:

> no se enteró

de:

> se enteró pero demoró en actuar.

---

# 30. Métrica: backlog sin responsable

Una asignación puede estar activa pero no tener ningún operador.

Regla conceptual:

```text
Periodo ACTIVO
+
0 SolicitudAsignacionUsuario activos
=
SIN RESPONSABLE
```

Ejemplo de dashboard:

```text
EXP-100    15 min sin tomar
EXP-102    2 h sin tomar
EXP-145    18 h sin tomar
EXP-170    2 días sin tomar
```

Esta métrica es extremadamente útil para supervisión.

---

# 31. Métrica: antigüedad de backlog

```text
unclaimed_age =
now()
-
Periodo.fecha_inicio
```

solo para períodos actualmente sin responsable.

Permite generar alertas:

```text
< 1 h
1–4 h
4–24 h
> 24 h
```

según el SLA posteriormente definido.

---

# 32. Métrica: tiempo hasta respuesta

```text
time_to_response =
respuesta.fecha_emision
-
periodo.fecha_inicio
```

Responde:

> ¿Cuánto tardó el área desde que recibió la intervención hasta emitir una respuesta?

---

# 33. Métrica: tiempo desde toma hasta respuesta

```text
time_claim_to_response =
respuesta.fecha_emision
-
primera_autoasignacion
```

Esto elimina del cálculo el tiempo durante el cual nadie había tomado el trabajo.

Permite diferenciar:

```text
demora organizacional
```

de:

```text
demora de elaboración.
```

---

# 34. Métrica: duración total del período

```text
cycle_time_periodo =
fecha_fin
-
fecha_inicio
```

Ejemplo:

```text
Arquitectura/P1

Inicio: 09:00
Fin:    17:00

Duración:
8 horas
```

---

# 35. Métrica: tiempo total acumulado por área

Una misma área puede tener varios períodos:

```text
Arquitectura

P1 = 5 horas
P2 = 3 horas
P3 = 4 horas
```

Entonces:

```text
Tiempo acumulado Arquitectura
= 12 horas
```

Permite medir cuánto tiempo de ciclo estuvo realmente asociado al área, aunque existieran devoluciones o reingresos.

---

# 36. Métrica: cantidad de reingresos

Si:

```text
Arquitectura
├── P1
├── P2
└── P3
```

entonces:

```text
periodos = 3
reingresos = 2
```

Puede señalar:

* retrabajo;
* derivaciones incorrectas;
* observaciones;
* problemas de calidad;
* procesos naturalmente iterativos.

---

# 37. Métrica: derivaciones

Desde `SolicitudDerivacion`:

```text
cantidad_derivaciones
```

por:

* solicitud;
* área;
* usuario;
* tipo de trámite;
* período;
* rango de fechas.

Ejemplo:

```text
Arquitectura

120 intervenciones
18 derivadas

Tasa derivación:
15%
```

---

# 38. Métrica: devoluciones

También puede medirse:

```text
cantidad_devoluciones
```

Ejemplo:

```text
A → B
B → A
```

Esto es especialmente relevante para evaluar la calidad del direccionamiento.

---

# 39. Métrica: rebotes

Ejemplo:

```text
A → B → A → B
```

El sistema puede detectar que existe un patrón de rebote.

Métricas posibles:

```text
número total de derivaciones
número de áreas únicas
cantidad de retornos
cantidad de ciclos
```

Por ejemplo:

```text
Derivaciones = 3
Áreas únicas = 2
Reingresos = 2
```

---

# 40. Métrica de primera asignación correcta

Puede ser especialmente útil para Mesa de Partes.

Ejemplo:

```text
100 solicitudes

82 nunca fueron derivadas por error
13 necesitaron una derivación
4 necesitaron dos
1 tuvo tres o más rebotes
```

Indicadores:

```text
First Assignment Accuracy
```

o conceptualmente:

```text
Porcentaje de solicitudes correctamente
direccionadas en la primera asignación.
```

---

# 41. Métrica: tasa de finalización

Por área:

```text
finalizadas
/
intervenciones recibidas
```

Siempre considerando correctamente el período analizado.

Ejemplo:

```text
Arquitectura

Recibidas:     120
Finalizadas:   108
Pendientes:     12
```

---

# 42. Métrica: rechazo

```text
periodos cerrados como RECHAZADOS
/
periodos recibidos
```

Permite detectar áreas a las que frecuentemente se les envía trabajo incorrectamente.

---

# 43. Métrica: retiro

```text
periodos RETIRADOS
/
periodos creados
```

Esto puede señalar:

* configuraciones erróneas;
* áreas agregadas innecesariamente;
* cambios administrativos;
* problemas en el diseño del trámite.

---

# 44. Métricas individuales

A nivel de usuario pueden obtenerse:

```text
notificaciones disponibles
notificaciones vistas
notificaciones nunca vistas

tiempo medio hasta vista
mediana hasta vista

asignaciones tomadas
tiempo medio hasta toma

participaciones iniciadas
participaciones finalizadas

respuestas emitidas

tiempo medio hasta respuesta

derivaciones ejecutadas
devoluciones ejecutadas

participaciones abandonadas
```

Sin embargo, estas métricas deben utilizarse con contexto operativo.

---

# 45. No evaluar exclusivamente por lectura

No sería recomendable utilizar:

```text
Juan vio 90%
Pedro vio 60%
```

como indicador aislado de rendimiento.

Un usuario podría no haber visto una notificación porque otro operador ya tomó inmediatamente el trabajo.

Una métrica individual debe entenderse junto con:

* rol;
* turno;
* disponibilidad;
* volumen asignado;
* autoasignaciones;
* respuestas;
* tiempo de resolución.

---

# 48. Mediana vs. promedio

Para métricas de tiempo es recomendable calcular:

```text
promedio
```

y:

```text
mediana
```

La mediana suele ser especialmente útil.

Ejemplo:

```text
9 solicitudes → 15 minutos
1 solicitud → 10 días
```

El promedio se distorsiona fuertemente.

La mediana refleja mejor el comportamiento habitual.

---

# 49. Percentiles

Posteriormente puede resultar útil utilizar:

```text
P50
P75
P90
P95
```

Ejemplo:

```text
Tiempo hasta toma

P50 = 18 min
P75 = 35 min
P90 = 2 h
P95 = 5 h
```

Esto permite detectar la cola problemática del proceso.

---

# 50. SLA

Las métricas también permiten establecer objetivos.

Ejemplo:

```text
Nueva asignación
→ alguien debe tomarla dentro de 2 horas.
```

Entonces:

```text
SLA toma = 2 horas
```

Se puede calcular:

```text
% tomadas dentro del SLA
```

y:

```text
cantidad actualmente fuera de SLA
```

No es necesario construir el sistema de SLA inmediatamente, pero los timestamps actuales permiten incorporarlo después.

---

# 51. Tiempo calendario vs. tiempo laboral

Esta consideración es muy importante si las métricas se utilizarán para evaluar desempeño.

Ejemplo:

```text
Viernes 17:55
→
Lunes 08:05
```

No debería necesariamente interpretarse como:

```text
62 horas de demora
```

si el área no trabaja fines de semana.

Posteriormente podrían incorporarse:

```text
CalendarioLaboral
Horario
Feriado
Turno
Ausencia
```

para calcular:

```text
business_elapsed_time
```

en lugar de simples diferencias de timestamp.

No es necesario implementarlo en la primera etapa, pero debe tenerse presente antes de utilizar métricas para decisiones sobre personas.

---

# 52. Métricas de calidad del proceso

No todo debe medir velocidad.

También conviene medir calidad:

```text
reingresos
rebotes
respuestas rectificadas
derivaciones incorrectas
devoluciones
periodos anulados
solicitudes reabiertas
```

Un proceso extremadamente rápido pero con mucho retrabajo puede ser peor que uno ligeramente más lento pero correcto.

---

# 53. Métrica de retrabajo

Ejemplo conceptual:

```text
Área Arquitectura tuvo:
P1
P2
P3
```

Si una única intervención normal debería requerir solamente P1, los reingresos pueden representar retrabajo.

Puede medirse:

```text
Solicitudes con >1 período del mismo área
/
Solicitudes donde participó el área
```

---

# 54. Métrica de colaboración

Con `SolicitudAsignacionUsuario` también se puede conocer:

```text
cantidad de usuarios por intervención
```

Ejemplo:

```text
Arquitectura/P1
Juan
Pedro
María
```

Esto permite detectar:

```text
intervenciones individuales
intervenciones colaborativas
```

Sin afirmar automáticamente que más usuarios sea mejor o peor.

---

# 55. Usuarios que participaron vs. usuario que respondió

Ejemplo:

```text
Arquitectura/P1

Juan   trabajó
Pedro  trabajó
María  revisó

Respuesta:
emitido_por = María
```

Las métricas pueden distinguir:

```text
participó
```

de:

```text
emitió respuesta
```

Esto evita atribuir todo el trabajo únicamente al usuario que presionó el botón final.

---

# 56. No crear inicialmente tablas de métricas

No se recomienda comenzar con:

```text
MetricasUsuario
MetricasArea
MetricasSolicitud
```

Las métricas deben derivarse inicialmente de las tablas transaccionales.

Las fuentes principales serían:

```text
Notificacion
NotificacionUsuario

SolicitudAsignacion
SolicitudAsignacionPeriodo
SolicitudAsignacionUsuario

SolicitudAsignacionRespuesta
SolicitudDerivacion

SolicitudEstadoHistorial
```

---

# 57. Por qué no persistir métricas inicialmente

Guardar directamente:

```text
promedio_respuesta = 5.3
cantidad_derivaciones = 12
```

crearía otra fuente de verdad que debe sincronizarse permanentemente.

Es preferible calcularlas de los eventos reales.

Posteriormente, si el volumen crece, pueden introducirse:

```text
materialized views
tablas agregadas diarias
warehouse
OLAP
ETL
```

sin modificar el núcleo transaccional.

---


Segunda etapa:

# 59. Tabla genérica de eventos


# 61. Interpretación de cada entidad

## `Notificacion`

> ¿Qué evento fue comunicado al área?

## `NotificacionUsuario`

> ¿Qué usuario tuvo disponible el aviso y cuándo lo vio?

## `SolicitudAsignacion`

> ¿Qué área participa en la solicitud?

## `SolicitudAsignacionPeriodo`

> ¿En qué ciclo temporal se encuentra esa participación?

## `SolicitudAsignacionUsuario`

> ¿Qué usuarios trabajaron ese ciclo?

## `SolicitudAsignacionRespuesta`

> ¿Qué respuesta formal produjo el área?

## `SolicitudDerivacion`

> ¿Cómo pasó el trabajo de un área/ciclo hacia otro?

## `SolicitudEstadoHistorial`

> ¿Cómo evolucionó globalmente la solicitud?

# 66. Regla fundamental para análisis

Debe distinguirse:

```text
TIEMPO DE ESPERA
```

de:

```text
TIEMPO DE TRABAJO
```

Por ejemplo:

```text
Área recibe            09:00
Juan toma              11:00
Respuesta              15:00
```

Entonces:

```text
Espera sin responsable:
2 horas

Trabajo desde toma:
4 horas

Tiempo total del área:
6 horas
```

Si solamente se mide:

```text
6 horas
```

se pierde información fundamental sobre dónde ocurrió realmente la demora.

# 67. Recomendación sobre rendimiento individual

Si las métricas se utilizan posteriormente para medir eficacia de trabajadores, se recomienda no construir un único "score" ingenuo.

Por ejemplo:

```text
más clics
=
mejor trabajador
```

sería una conclusión incorrecta.

Es preferible analizar varias dimensiones:

```text
capacidad de reacción
cantidad de trabajo asumido
tiempo de resolución
calidad
retrabajo
colaboración
carga recibida
cumplimiento de SLA
```

Y siempre distinguir:

```text
responsabilidad del usuario
```

de:

```text
rendimiento institucional del área.
```

# 69. Principio final

El sistema debe registrar **hechos**, no únicamente resultados agregados.

Ejemplos de hechos:

```text
La notificación se creó a las 09:00.

Pedro la vio a las 09:04.

Juan la vio a las 09:07.

Juan tomó el trabajo a las 09:12.

María emitió la respuesta a las 13:45.

El área terminó a las 14:00.
```

A partir de esos hechos pueden calcularse todas las métricas necesarias.

Ese enfoque permite cambiar posteriormente:

* fórmulas;
* KPIs;
* SLAs;
* dashboards;
* criterios de desempeño;

sin perder información histórica ni modificar las tablas fundamentales.

## Conclusión

La arquitectura operativa debe mantener separadas cuatro dimensiones:

```text
COMUNICACIÓN
Notificacion / NotificacionUsuario

RESPONSABILIDAD
SolicitudAsignacion / Periodo

EJECUCIÓN HUMANA
SolicitudAsignacionUsuario

RESULTADO
SolicitudAsignacionRespuesta
```

Las derivaciones y el historial de solicitud complementan el proceso.

Con este modelo es posible medir tanto el desempeño institucional del área como el comportamiento operativo de los usuarios, sin confundir:

```text
ver
```

con:

```text
tomar
```

ni:

```text
tomar
```

con:

```text
responder/finalizar.
```

Ese desacoplamiento es lo que permite construir métricas fiables y evolucionar posteriormente hacia dashboards operativos, SLA y análisis de desempeño sin rediseñar nuevamente el núcleo del sistema.
